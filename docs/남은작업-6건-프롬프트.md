### 반드시 지킬 것

- **커밋에 `Co-Authored-By: Claude` 를 넣지 않는다.** 팀 정책이다. PR 본문도 마찬가지.
- 커밋 메시지는 *무엇을 고쳤나*가 아니라 **왜 그랬나**를 쓴다. 이 브랜치의 기존 커밋이 본보기다.
- 모든 컨트롤러 응답은 `ApiResponse<T>` 로 감싼다. 경로는 `/api/v1/...`.
- 엔티티에 `@Setter` 금지. 변경은 의도가 드러나는 메서드로.
- `ddl-auto: validate` 다. **컬럼을 추가하면 마이그레이션을 운영에 먼저 적용해야 부팅된다.**
- **CHECK 제약은 `ddl-auto: update` 로 안 고쳐진다.** enum 값을 늘리면 반드시 마이그레이션.
  (이 프로젝트에서 이미 두 번 사고가 났다.)
- 테스트는 Mockito 단위 + `@WebMvcTest` 슬라이스. DB·Redis 없이 돈다. 현재 539개.

### 검증할 때의 함정 — 이번 세션에서 두 번 오진했다

1. **Postgres 정규식으로 `<script>…</script>` 를 지우면 본문까지 날아간다.**
   Postgres 는 RE 전체에 성향 하나를 적용해서 `.*?` 가 탐욕처럼 동작한다.
   → SQL 에서는 `regexp_replace(raw_html, '<[^>]+>', ' ', 'g')` 한 단계만 쓴다.

2. **`scholarship_condition` 에 `raw_scholarship` 을 조인하면 행이 부풀어 오른다.**
   원본 둘이 같은 장학금을 가리키면 조건이 두 배로 세어진다.
   → 집계는 서브쿼리나 `DISTINCT` 로. 조인 뒤 `count(*)` 를 믿지 말 것.

3. **파서 결과 검증은 `notice_parse_log.body_text` 를 쓴다.** 원본(`raw_html`)을 다시
   벗겨 재현하지 말 것. 그 재현이 틀려 "셀렉터가 빗나갔다"고 두 건을 오진했는데,
   실은 본문을 제대로 뽑고 있었다.

## 2. 응답에 `rankerVersion`·`section` 을 내려준다 — 측정이 여기서 끊긴다

### 왜

서버는 `scholarship_event.section` · `ranker_version` 을 받을 준비가 끝났는데,
**프론트가 무엇을 실어 보낼지 알 방법이 없다.** 프론트가 `"v2"` 를 하드코딩하면
점수식을 올릴 때마다 프론트도 같이 배포해야 하고, 안 하면 판 비교 자체가 불가능하다.

조사 자료의 1단계("알고리즘 변경이 아니라 수집을 실제로 작동시키는 것")가 여기서 반쪽이다.

### 무엇을

`src/main/java/com/wishconnect/domain/scholarship/dto/CuratedScholarshipResponse.java`

- 최상위에 `String rankerVersion` 추가. 값은 `ScholarshipRanker.RANKER_VERSION`.
- `ScholarshipCard` 에 `String section` 추가. 각 섹션에서 카드를 만들 때 채운다.
  `featured` / `campus` / `other` / `ineligible` — 문자열 상수로 한곳에 모아 둘 것.

`ScholarshipRecommendationService` 의 `toCard(...)` 가 섹션을 모르므로 인자를 하나 늘린다.
`ScholarshipCard.of(...)` 시그니처도 함께.

### 확인

- `GET /api/v1/scholarships/curated` 응답에 두 값이 나온다.
- 프론트가 그 값을 그대로 `POST /api/v1/scholarships/events` 에 실어 보내면
  `scholarship_event` 에 섹션·판이 남는다.

### 테스트

섹션마다 카드의 `section` 이 맞게 붙는지 한 개. 응답의 `rankerVersion` 이
`ScholarshipRanker.RANKER_VERSION` 과 같은지 한 개.

## 3. 관리자 `ALWAYS_OPEN` 목록 + 마감 처리 — 지금은 수기처리가 불가능하다

### 왜

`ALWAYS_OPEN` 은 마감일이 없어 자동으로 닫을 수 없는 공고다("충원 시 마감", "모집 마감",
자동선발). 20건 있다. 관리자 개요(`GET /api/v1/scholarships/admin/overview`)에
`alwaysOpen` 건수는 나가는데 **그 20건을 목록으로 보고 닫는 수단이 없다.**
숫자만 보이고 처리할 방법이 없으니 영원히 20건이다.

### 무엇을

**목록 API**

```
GET /api/v1/scholarships/admin/always-open?page=0&size=20
```

`ScholarshipAdminController` 에 추가한다(클래스에 이미 `@PreAuthorize("hasRole('ADMIN')")`
가 걸려 있다). 응답 항목에 판단에 필요한 것만 담는다 —
`id · title · provider · createdAt · 조건 수 · 원문 링크(detailUrl 또는 homepageUrl)`.
**원문 링크가 핵심이다.** 관리자가 열어 보고 닫을지 정한다.

정렬은 `createdAt` 오름차순. 오래된 것부터 처리하는 게 자연스럽다.

**마감 처리는 새로 만들지 말 것.** 이미 있다.

```
PATCH /api/v1/scholarships/manual/{scholarshipId}
```

`ScholarshipManualRequest` 로 부분 수정이 되고, `AdminAction.SCHOLARSHIP_UPDATE` 로
감사 로그까지 남는다. `recruitmentStatus` 를 이 요청으로 바꿀 수 있는지 확인하고,
안 되면 **그 필드만** 열어 준다.

⚠️ 감사 로그의 `AdminAction` 에 새 값을 추가하려면 `admin_audit_log_action_check`
제약 마이그레이션이 필요하다. 예전에 이걸 빼먹어서 감사 기록 실패가 트랜잭션을
롤백으로 만들었고 백필 전체가 날아간 적이 있다. **기존 값(`SCHOLARSHIP_UPDATE`)을
쓰면 이 문제가 없다.**

### 확인

목록에 20건이 나오고, `PATCH` 로 하나를 `CLOSED` 로 바꾸면 목록에서 빠진다.

## 4. `featured`·`campus` 섹션 정렬을 채운다

### 왜

랭커를 만들었는데 **`other` 섹션에만 적용했다.** 나머지는 예전 그대로다.

`ScholarshipRecommendationService` 현재 상태:

```java
// featured — 마감일 오름차순만. 점수를 안 본다.
.filter(s -> s.dDay() != null && s.dDay() >= 0)
.sorted(Comparator.comparingLong(ScoredScholarship::dDay))
.limit(FEATURED_LIMIT)   // 5

// campus — 필터만 있고 정렬이 아예 없다. 순서가 사실상 무작위다.
.filter(s -> s.scholarship().getScholarshipType() == ScholarshipType.INTERNAL)
.filter(s -> isSameSchool(s.scholarship(), profile))
```

### 무엇을

**featured (피그마 1번 — 상위 5개 캐러셀)**
마감 임박만 보면 점수가 낮은 공고도 올라온다. 마감이 가까운 것 중에서 **점수순**으로
5개를 고른다. 예: `dDay <= 14` 로 후보를 좁힌 뒤 `matchScore` 내림차순, 동점이면 `dDay` 오름차순.
후보가 5개에 못 미치면 기간을 넓힌다.

**campus (피그마 2번 — 교내 장학금)**
사용자가 "추천 말고 그냥 교내 전체 보기"라고 했으므로 점수로 재배열하지 않는다.
다만 **정렬이 없는 건 안 된다.** 마감 임박순으로 고정한다(마감 없는 것은 뒤로).

**ineligible (피그마 3번)**
점수순은 유지하되 `ScholarshipRanker.diversify` 를 적용한다. 한 기관이 덮는 건
여기서도 똑같이 일어난다.

### 테스트

featured 가 마감 임박만이 아니라 점수도 반영하는지 한 개.
campus 가 마감 임박순인지 한 개.

## 5. 장학금 상세 화면

`docs/추천-상세-작업인계.md` 에 상세히 적어 뒀다. **그 문서를 먼저 읽을 것.** 요약하면:

**5-1. 자격 판정·추천 이유를 화면 위로**
`ScholarshipDetailService` 는 이미 `conditionChecks`(충족/불충족/판정불가)와
`matchReasons` 를 내려준다. DTO 에는 있는데 화면에 자리가 없다. 순서를 이렇게 바꾼다.

```
상단  제목 · D-day · 마감일시 · 웹사이트 / AI 지원서 배너   (그대로)
신규  내 자격 판정 — 조건별 ✓/✗/? + 추천 이유
      자소서 · 면접 필요 여부 + 근거 문장
중단  포스터 + 요약정보 (있는 것만, 가변)
하단  제출서류 체크리스트 + 제출방법 · 마감 시각
```

**5-2. 선발 일정 섹션은 접는다**
피그마의 `서류접수 → 서류발표 → 면접전형 → 최종발표` 4단계는 **채울 데이터가 없다.**
파서가 본 본문 40건 조사 결과 `발표 일자 0/40 · 면접 일자 1/40`. 대학 공지는
발표 일정을 안 적는다. 프롬프트를 고쳐도 없는 걸 만들어낼 뿐이다.
마감일 하나를 크게 보여주고, 면접 여부(27% 채워짐)를 따로 표시한다.

**5-3. 요약정보를 가변 목록으로**
14칸 고정인데 채움률이 0~100% 로 들쭉날쭉하다(모집중 132건 기준).

```
운영기관 100% · 제출방법 89% · 중복지원 64% · 성적기준 44%
선발기준 33% · 소득기준 32% · 지원금액 33% · 선발인원 35%
지원형태 19% · 지원분야 11% · 문의처 0%
```

값이 있는 항목만 채움률 순으로 낸다.

## 6. v6 프롬프트 — 문의처 + 배포

### 6-1. 문의처만 추가한다

`ScholarshipDetailService.buildSummary` 가 `contactInfo` 자리에 **`null` 을 하드코딩**하고
있다. 본문에는 있다 — 문의처 언급 70% · 전화번호 58% · 이메일 48%.

`UnivNoticeLlmParser`:
1. `PROMPT_VERSION` 을 `"v6"` 으로
2. 출력 형식에 `"contact": 문자열|null`
3. 판별 기준 한 줄: *문의처는 담당 부서·전화·이메일이다. 서류를 내는 경로와 구분한다.*
   (v5 에서 "문의처는 제출 경로가 아니다" 를 이미 넣었으니 반대 방향도 명확히 할 것)
4. `ParsedNotice` 에 `contact` 필드 — **반드시 뒤에 붙인다.** 레코드 중간에 끼우면
   위치로 호출하는 곳이 조용히 깨진다(실제로 겪었다).
5. `Scholarship` 에 `contact` 컬럼 + 마이그레이션
6. `buildSummary` 의 `null` 을 `scholarship.getContact()` 로

**금액·선발인원은 재파싱해도 이득이 없다.** 이미 33%·35% 를 뽑는데 본문에 있는 비율이
15%·38% 다. 원문에 없는 것이다. 손대지 말 것.

### 6-3. v6 재파싱

**크레딧이 든다. 사용자에게 어드민 토큰을 받고, 사용자가 돌리라고 할 때만 돌린다.**
