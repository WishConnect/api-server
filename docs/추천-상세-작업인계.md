## 남은 작업 — 4단계: 상세 화면 + v6

### 4-1. 상세 화면에 자격 판정과 추천 이유를 올린다

`ScholarshipDetailService.buildDetail` 은 이미 `conditionChecks`(충족/불충족/판정불가)와
`matchReasons` 를 내려주고 있다. **DTO 에는 있는데 피그마 화면에 자리가 없다.**

화면 순서를 이렇게 바꾸기로 사용자와 합의했다.

```
상단   제목 · D-day · 마감일시 · 웹사이트        (그대로)
       AI 지원서 배너                          (그대로)
신규   내 자격 판정 — 조건별 ✓/✗/? + 추천 이유
       자소서 · 면접 필요 여부 + 근거 문장
중단   포스터 + 요약정보 (있는 것만, 가변 목록)
하단   제출서류 체크리스트 + 제출방법 · 마감 시각
       선발 일정 — 접는다 (아래 참조)
```

### 4-2. 선발 일정 섹션은 접는다

피그마는 `서류접수 → 서류발표 → 면접전형 → 최종발표` 4단계를 그리는데
**채울 데이터가 없다.** 파서가 본 본문 40건을 조사한 결과:

```
발표 일자가 날짜와 함께 적힌 건    0 / 40
면접 일자가 날짜와 함께 적힌 건    1 / 40
```

대학 공지는 발표 일정을 안 적는다. 적어도 "12월 예정", "추후 개별 안내" 수준이다.
프롬프트를 고쳐도 원문에 없는 걸 만들어낼 뿐이다.

대신 마감일 하나를 크게 보여주고, 면접 여부(36/132 = 27% 채워짐)를 별도 표시한다.

### 4-3. 요약정보를 가변 목록으로

지금 `Summary` 는 14칸 고정인데 채움률이 고르지 않다. 모집중 132건 기준:

```
운영기관 100%   제출방법 89%   중복지원 64%   성적기준 44%
선발기준 33%    소득기준 32%   지원금액 33%   선발인원 35%
지원형태 19%    지원분야 11%   문의처 0%
```

고정 2열 14칸으로 그리면 빈칸이 눈에 띈다. **값이 있는 항목만** 채움률 순으로 낸다.

### 4-4. v6 프롬프트 — 문의처만 추가

`ScholarshipDetailService.buildSummary` 가 `contactInfo` 자리에 `null` 을
하드코딩하고 있다. 본문에는 있다:

```
문의처 언급    28 / 40   (70%)
전화번호       23 / 40   (58%)
이메일         19 / 40   (48%)
```

`UnivNoticeLlmParser` 에 할 일:
1. `PROMPT_VERSION` 을 `v6` 으로
2. 출력 형식에 `"contact": 문자열|null` 추가
3. 판별 기준에 한 줄: 문의처는 담당 부서·전화·이메일. 신청 경로와 구분한다.
4. `ParsedNotice` 에 `contact` 필드 (뒤에 붙일 것 — 중간 삽입 금지)
5. `Scholarship` 에 `contact` 컬럼 + 마이그레이션
6. `buildSummary` 의 `null` 자리를 `scholarship.getContact()` 로

**금액·선발인원은 재파싱해도 이득이 없다.** 이미 33%·35% 를 뽑고 있는데
본문에 있는 비율이 15%·38% 다. 원문에 없는 것이다.

## 이 저장소에서 반드시 지킬 것

### 검증 쿼리를 스스로 검증할 것

이번 세션에서 검증 쿼리 때문에 **두 번 오진했다.**

1. Postgres 정규식으로 `<script>…</script>` 를 지우려다 본문까지 날렸다.
   Postgres 는 RE 전체에 성향 하나를 적용해서 `.*?` 가 탐욕처럼 동작한다.
   → SQL 에서는 `regexp_replace(raw_html, '<[^>]+>', ' ', 'g')` 한 단계만 쓴다.

2. `scholarship_condition` 에 `raw_scholarship` 을 조인해 행이 부풀었다.
   원본 둘이 같은 장학금을 가리키면 조건이 두 배로 세어진다.
   → 집계는 서브쿼리나 `DISTINCT` 로. 조인 뒤 `count(*)` 를 믿지 말 것.

**파서 결과를 검증할 때는 `notice_parse_log.body_text` 를 쓴다.**
원본(`raw_html`)을 다시 벗겨 재현하면 안 된다. 그 재현이 틀려서
"셀렉터가 빗나갔다"고 두 건을 오진했는데, 실은 본문을 제대로 뽑고 있었다.
