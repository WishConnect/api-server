# 장학금 이미지·선발 일정 백엔드 수정

작업 브랜치: `fix/scholarship-image-schedule` (최신 `develop` `bbf5253` 기반).
팀의 Java/Spring 컨벤션을 확인했으며 새 코드는 4 spaces, camelCase/PascalCase, 기존 도메인 패키지와 공통 예외를 사용합니다. 기존 DB 테이블 이름은 현재 스키마를 유지합니다.

## 이미지

- `PosterImageSelector`를 대학 공지 수집과 상세페이지 보완 수집에서 공유합니다. 본문·이미지 첨부를 먼저 선택하고, 대학 공통 로고(`UI_Mark_view` 포함), 배너, 헤더·메뉴 이미지, 작은 아이콘을 제외합니다. 본문 구조를 모르면 임의의 첫 이미지를 가져오지 않습니다.
- 상세·추천·검색·보관함·관리자 이미지 목록과 관리자 교체의 대표 이미지 기준을 통일했습니다. 기존 S3 경로 규약의 `scholarships/admin/`, `scholarships/manual/`를 관리자 검수 출처로 보고 우선하며, 같은 출처에서는 최신 이미지 행을 선택합니다.
- 자동 재수집은 대표 행을 갱신하며 관리자 이미지를 보존합니다. 저장 직전에는 행 잠금과 refresh로 다른 트랜잭션의 관리자 교체도 확인합니다. S3 객체 키는 UUID로 분리해 예전 객체와 캐시를 덮어쓰지 않습니다.
- 다운로드를 스트림으로 제한해 자동 수집 10MB, 관리자 5MB 한도를 유지합니다. PNG/JPEG/GIF/WebP Content-Type을 정규화합니다. 실제 픽셀 디코딩 검사는 이번 변경에 포함하지 않았습니다.
- 이미 장학금에 연결된 이미지 전용 원문은 재파싱할 때 LLM 호출 없이 자동 포스터를 다시 선택할 수 있습니다.

현재 운영에 저장된 잘못된 이미지 자체를 수정하거나 S3 객체를 삭제하지는 않았습니다. 관리자 검수 출처로 저장된 잘못된 이미지는 원문 확인 후 기존 이미지 교체 기능으로 교정해야 합니다.

## API 수집과 크롤링·파싱 경로 검토

| 경로 | 기존 상태 | 변경 |
|---|---|---|
| 대학 공지 크롤링 → raw_html → UnivNoticeLlmParser | 원문을 읽지만 파싱 결과 스키마에 선발 일정 목록이 없음 | 프롬프트 v7·구조화 출력에 timeline 추가, 검증 후 저장 |
| 공공데이터 API → 자유 텍스트 조건 파싱 | 조건·서류·전형 정보만 저장 | 선발 방법 등의 텍스트에 근거가 있는 일정도 저장, 제목·금액·모집기간은 보존 |
| 공공데이터 공고 → 상세 URL 검색 → 상세페이지 크롤링 | 이미지·첨부 링크만 수집 | 해당 상세 본문에서 LLM으로 일정 추출·저장 |

`NoticeTimelineParser`는 단계와 날짜를 포함한 원문 인용을 검증합니다. 없는 날짜·잘못된 연도·다른 단계의 날짜·역순 기간은 버립니다. 연도 없는 월일은 수집 기준일과 원문의 앞 날짜를 사용하며, 원문에 명시된 미정 문구를 보존합니다. 접수 단계는 기존 모집기간 검증과 응답 대체 로직으로 처리합니다.

`CrawledScholarshipTimelineService`는 검증된 일정을 `origin=LLM`으로 저장합니다. 자동 응답이 없거나 잘못됐을 때 기존 일정을 지우지 않습니다. 관리자 수기 일정, 수기로 비운 일정, 감사 기록에서 복구한 일정은 자동 파싱으로 변경하지 않습니다. 병합 시에도 수기 보호를 유지합니다.

본문이 이미지·PDF/HWP 첨부에만 있는 공고는 현 파이프라인에서 별도 OCR/문서 본문 추출이 필요합니다. 이미지 alt에 실제 내용이 있으면 기존 본문 추출 경로로 처리할 수 있습니다. 날짜를 추측해 채우지는 않습니다.

추가 응답 필드:

- 관리자 상세 `scholarship.timelineLocked`: 수기 저장·삭제·복구를 자동 추출에서 보호하는지.
- 파싱 결과 `items[].timelineCount`: 원문 근거 검증을 통과한 일정 후보 수. 수기 보호 때문에 실제 저장 수와 다를 수 있습니다.
- 상세페이지 보완 결과 `timelineSaved`: 실제 저장한 일정 행 수.

기존 공개 상세 `selectionSchedule`의 `step/date/status` 구조와 미정 상태의 UPCOMING 호환 처리는 유지합니다.

## 배포와 기존 데이터 보완

1. 새 백엔드 배포 전에 `V20261008_01__scholarship_timeline_locked.sql`을 적용합니다. 운영 마이그레이션은 자동 실행되지 않습니다. `V20261006_01` 적용 상태도 확인합니다.
2. 새 SQL은 `scholarship.timeline_locked`를 추가하고 기존 MANUAL 일정이 있는 공고를 보호 상태로 채웁니다. 과거에 이미 삭제되어 행이 없는 수기 일정은 이 백필만으로 삭제 의도를 판별할 수 없으므로 운영 검수에서 확인해야 합니다.
3. 백엔드를 배포한 뒤 소수 공고부터 재수집·재파싱하고 원문 → API → 화면을 대조합니다.
4. 대학 공지는 관리자 콘솔에서 수집/원문을 확인한 다음 `POST /api/v1/scholarships/parse/univ-llm`을 사용합니다. 먼저 `dryRun=true`로 일정 후보를 확인하고 필요한 rawIds만 지정합니다. rawIds는 장학금 ID가 아니라 원본 ID입니다. 새 프롬프트 버전에서 일정 없는 공고도 불완전 재파싱 대상으로 들어갑니다.
5. 공공데이터의 상세페이지 보완은 기존 `POST /api/v1/scholarships/enrich`에 연결했습니다. 기존 대상 선택·검색 신뢰도·14일 재시도 정책을 따릅니다.
6. `SCHOLARSHIP_ENRICH_COLLECT_SCHEDULE` 기본값은 true입니다. 상세페이지의 읽을 본문이 있으면 공고당 LLM 호출이 추가됩니다. false로 설정하면 이 보완 수집의 일정 추출만 끕니다. 대학 공지·공공데이터 텍스트 파싱의 timeline 출력은 기존 LLM 호출에 포함됩니다.

운영 배포·운영 SQL 실행·유료 LLM 호출·기존 운영 데이터 재파싱은 이 작업에서 수행하지 않았습니다.

## 검증

- `./gradlew build`: 전체 922개 테스트 통과(실패·오류·건너뜀 0), 실행 JAR 빌드 검증.
- 회귀 테스트: 로고 대신 본문 포스터 선택, 상대 URL, 작은 아이콘/메뉴 제외, 관리자 이미지 보존, 같은 대표 행 교체, 자동 재수집 객체 키 분리, 일정 근거 검증, 미정 문구, 잘못된 날짜·연도·단계 연결 거부, 수기 삭제 보호, 크롤링 일정의 상세 응답 조립.
- 임시 PostgreSQL 16·Redis와 qa 설정으로 실제 Spring Boot 서버를 실행했습니다. 운영 자격증명과 데이터를 사용하지 않았고 수집·알림 스케줄을 비활성화했습니다.
- 임시 DB에서 새 SQL 적용·재적용과 기존 MANUAL 일정의 수기 보호 백필을 확인했습니다. 적용 후 `ddl-auto=validate`로 정상 기동했습니다.
- 실제 HTTP 목록·상세에서 더 최신 자동 이미지가 있어도 같은 관리자 이미지가 선택됨을 확인했습니다. 모집기간 대체와 서류 발표·면접 기간·최종 발표·미정 지급 일정을 포함한 5단계가 응답되었습니다.
- 실제 S3 업로드·외부 LLM 추출 정확도·프론트엔드 화면 반영은 운영 통합 검증이 필요합니다.

프론트엔드 담당 작업은 이미지 cover/겹침 제거, 날짜 전체 표시, 4단계 제한 제거입니다. 백엔드 응답에는 전체 일정과 기간 문자열이 포함됩니다.
